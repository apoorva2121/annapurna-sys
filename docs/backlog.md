# Backlog

Ideas that arrived mid-module. **Nothing here is scope** until it is promoted into
`docs/modules.md` deliberately, between modules — never during one.

This file exists because the vision document has 36 sections and the single most reliable way to
finish nothing is to act on all of them.

| One person who genuinely works for two restaurant groups cannot use one identifier | M01, 2026-09-10, **revised 2026-09-11** | Originally filed as "an ambiguous identifier locks that person out". An independent review found the sharper half: the clash check was org-scoped while login resolution is global, so *any tenant could deliberately take another tenant's identifier and lock its owner out permanently*. That is now fixed — creating a login refuses an identifier held anywhere in the product (`UserAccountRepository.identifier_is_taken`), and `tests/test_review_regressions.py` holds it. **The cost of that fix is this entry**: an accountant who really does work for two restaurant groups can no longer use one email for both, and now gets a plain "already in use" when the second group adds them. That is the right trade — an availability hole that any trial account could exploit beats an inconvenience for a rare, legitimate case — but it is a real regression in capability and should not be discovered later as a surprise. Proper fix is a per-tenant login surface (subdomain) or an organization picker, at which point identifiers can go back to being per-tenant unique. |

| Global identifier uniqueness is enforced by code, not by the database | M01, 2026-09-11 | `user_account` constrains `(organization_id, email)` and `(organization_id, phone)` per tenant. The product now also requires identifiers to be unique *globally*, because login resolves across organizations — but that rule lives only in `_create_login` and the seed. Two concurrent creates in different organizations can both pass the check and both insert, and CLAUDE.md invariant 1 is explicit that this class of rule should be structural rather than conventional. **Deliberately not fixed in M01.** A global unique index would work, and would also permanently foreclose the per-tenant login surface (subdomain, or an organization picker) that the row below names as the proper fix — after which identifiers correctly go back to being per-tenant unique and the global index has to be dropped again. Adding a constraint we expect to remove is worse than carrying a documented race that requires an attacker to win a timing window against an account being created. Revisit **with** that row, not before: whichever is built first decides the other. |
| Lockout reveals whether an identifier exists | M01, 2026-09-11 | `AuthService._reject_if_locked` runs *before* the password is verified, so five wrong guesses against a real identifier return `429 auth.locked` while an identifier nobody holds returns `401 auth.invalid_credentials`. That is an enumeration oracle sitting next to a login path built specifically to avoid one. Found by an independent review of M01. **Accepted for now**, because the alternative is refusing to tell a locked-out waiter why they cannot sign in at 7pm on a Saturday. Fix properly with rate limiting by IP rather than by account, so the signal stops being per-identifier. Revisit in M14 with the rest of the security hardening. |
| Two stale tabs refreshing at once sign each other out | M01, 2026-09-11 | The single-flight in `shared/api.ts` is per-tab. Two tabs whose access tokens expire together each present the same refresh cookie; one is a replay, and `_handle_replay` correctly revokes the whole family — so a person with two tabs open over lunch is signed out of both. Correct behaviour from a stolen-token standpoint, poor behaviour from a real one. Fix needs cross-tab coordination (a `BroadcastChannel` lock, or moving refresh into a service worker). Not worth it in M01; worth it before staff actually use the product on a shared tablet. |

| Share business-day test vectors between Python and TypeScript | M02, 2026-09-11 | The rule now has two implementations (`backend/app/core/business_day.py`, `frontend/src/shared/businessDay.ts`) and ADR 0004 forbids a third. | ruff's `DTZ` rules (naive datetime) are not enabled | M02, 2026-09-11 | CLAUDE.md invariant 4 is that time is stored UTC and aware; `business_date_of` refuses a naive datetime at runtime. `DTZ` would catch `datetime.now()` without a timezone at the lint stage instead, which is where it is cheap. | Drag to reorder the floor plan | M02, 2026-09-11 | **A deliberate deviation from the approved spec, recorded rather than done quietly.** The M02 spec says "dining areas and tables (drag to reorder)"; chunk E shipped move-up/move-down buttons instead. Reasoning: drag needs a library (dnd-kit or similar), and to be usable at all it needs a keyboard path built alongside it — which is what the buttons already are. Buttons also work with a glove and a steamed-up screen, which is the surface constraint `docs/ui/conventions.md` cares about, and they write the same `seq` the server already understands. Adding drag later is purely additive: no data changes, no API changes, and the buttons stay as the keyboard path. Do it when someone with a real floor plan says the buttons are slow — that is evidence; "the spec said drag" is not, on its own, worth a dependency. |
| Reordering costs two requests and is not atomic | M02, 2026-09-11 | Moving a dining area swaps its `seq` with its neighbour's, which is two `PATCH`es from the browser. If the second fails, two areas share a `seq` — the list stays deterministic because the query orders by `(seq, id)`, so nothing breaks visibly, but the order is not what the person asked for and nothing says so. The fix is a `POST /setup/dining-areas/reorder` taking the whole ordering, which is one request, atomic, and also what a drag implementation would want. Left out of M02 because the failure is cosmetic and self-correcting on the next move; do it **with** the drag row above, since they want the same endpoint. |
| A superseded tax rate has nothing pointing at its successor | M02, 2026-09-11, **found by M02's own adversarial review** | `docs/schema.md` §3 gives `menu_item_variant` a `tax_group_id` that references one `tax_group` row directly. M02's rule (spec decision 2) is that a rate change is a **new row** and the old one gets an `effective_to`. Put together: when a rate is replaced, every menu item still points at the closed row and nothing links it to the replacement. **History is safe** — `order_line.tax_rate` is copied at order time, so past invoices keep the rate they charged. What is missing is the forward step: on a changeover somebody must re-point every menu item at the new rate, and neither a mechanism nor a screen for that exists, so it is a manual bulk operation nobody has designed and nobody will remember. `seed/operations.yaml` already gives each rate a `code` (`GST5`, `GST18`) which is exactly the stable family key this needs, and the schema has no column for it. **Recommended fix:** add `tax_group.code`, unique on `(restaurant_id, code, effective_from)`, inherited by a replacement from the row it supersedes, so a menu item references the *family* and the effective row is resolved by date. **Not done in M02** because it changes an approved schema and M06 is the module that first depends on it — but it is far cheaper before M06 creates foreign keys pointing at these rows than after. **Un-defer: the moment M06 starts.** |
| `switch_restaurant` fabricates a session id it does not use | M02, 2026-09-11 | `LoginResult.session_id` is required by the dataclass, `actor.session_id` is usually `None`, so the switch passes `uuid7()` — a freshly minted id for a session that already exists. Nothing reads it on this path (`_session_response` ignores it), so it is harmless today and dishonest tomorrow: the next person to use `result.session_id` after a switch gets a number that matches no row. Fix is either an optional field or a narrower return type for this one call. Small, and worth doing when `LoginResult` is next touched. |
| Refresh-rotation grace window for honest double-refreshes | M02, 2026-09-11, **external review** | `refresh()` now claims the session row atomically, so two concurrent refreshes cannot both mint a session. The loser is treated as a replay and `revoke_family` signs the person out **everywhere** — which is correct for theft and wrong for two tabs waking from sleep, a retried request after a timeout, or a service worker and a page refreshing together. Restaurant staff on a flaky network will hit this. The standard fix is a reuse grace window: add `rotated_to_id` to `user_session`, and in `_handle_replay`, if the presented row was revoked within ~10 seconds *and* its successor is still live and unused, return that successor instead of killing the family. That distinguishes "two tabs" from "two parties", which the current code cannot do at all. **Un-defer when the first person reports being logged out mid-shift**, or with M14's security hardening, whichever comes first. |
| `IntegrityError` is unmapped, so every check-then-insert race is a 500 | M02, 2026-09-11, **external review** | Every conflict in `SetupService` is a pre-check (`name_exists`, `code_exists`) followed by an INSERT. The repository comments are honest that "the unique constraint is still the authority — this is a better message, not the guarantee" — but when the constraint fires, `IntegrityError` reaches the catch-all handler and becomes `500 internal.error`. Two admins adding "Terrace" at the same moment, or a duplicate submit on a flaky connection, get a reference number instead of the conflict the pre-check exists to spell nicely. There is no `IntegrityError` handler anywhere in `backend/app/`. Fix: one handler in `register_error_handlers` mapping SQLSTATE 23505 → 409 and 23514 → 422, constraint name in the log only, never the body. Keep the pre-checks — they give the good message on the common path; the handler covers the race. |
| Server-owned form state is never reconciled after a save | M02, 2026-09-11, **external review** | `RestaurantSettingsScreen` and `ThemeSection` copy server values into `useState` once and never re-seed. The reachable case: type `inr`, save, the server normalises to `INR`, the query refetches — and the form still holds `inr` while displaying `INR` through a CSS `uppercase`. The screen shows a green "Saved" over a value the database does not hold. Worse for the theme: `RestaurantChanges.theme` is sent whole by design, so a schedule edited in another tab is overwritten silently on the next Save — a lost update with no ETag and no warning. Fix in two steps: re-seed from the PATCH response (cheap, closes the currency case), then `version`/`updated_at` on `restaurant` and a conditional PATCH so a concurrent edit is a 409 the user sees. **Do the second before the settings surface grows.** |
| Deactivating an area races a table being created in it | M02, 2026-09-11, **external review** | `update_dining_area` counts active tables and `_require_area` checks `is_active`, neither under a lock. Two admins — an owner on a laptop, a manager on a tablet, which is exactly a restaurant opening — can deactivate an area and add a table to it concurrently, leaving an active table in a deactivated area. It appears in no area-filtered list and will be seated by M07. Fix: `DiningAreaRepository.get_for_update`, used by both paths, mirroring what `TaxGroupRepository` already does. |
| `migration 0005` reads the live catalogue file at migration time | M02, 2026-09-11, **external review** | `_reconcile_catalogue()` reads `app/core/permissions.json` when it *runs*, not as it was when written, so a database stopped at 0004 and upgraded later applies a catalogue from the future — and its wholesale `DELETE FROM role_permission` reconciles against it. Benign today because the reconcile is idempotent and later migrations redo it; it stops being benign the first time a permission is **removed** from the file, at which point replaying 0005 revokes a grant later revisions assume is present, and its `downgrade()` withdraws only `restaurant.configure`. Fix: inline the rows this revision introduces rather than reading the file; the fingerprint test still forces a migration per catalogue edit. **Un-defer with M03's first permission**, which is when the second catalogue edit proves the fingerprint test still works after the change. |
| `MeResponse.restaurants` is unbounded | M02, 2026-09-11, **external review** | No limit, no cursor, and `/auth/me` is called on every app load — the worst list to let grow silently. Invisible for a single-branch pilot; the product's stated direction is restaurant groups. Cap the embedded list at ~20 for the switcher and add `GET /staff/restaurants` with a cursor for the overflow, before M03 makes `/auth/me` hot. |
| Table `status` is editable through the setup PATCH with no transition guard | M02, 2026-09-11, **external review** | `TableUpdateRequest.status` accepts all five values and the service applies any of them, so an owner can set a table to `free` while an order is open on it. Harmless now — no orders exist — and an orphaned open order the moment M07 lands. The right shape is `POST /setup/tables/{id}/status` with an explicit allowed-transition table and `status` removed from the general update, exactly as `is_active` was removed from `EmployeeUpdateRequest` for the same reason. **Un-defer with M07.** |
| Two live tax rates of different names, and no class discriminator | M02, 2026-09-11, **external review** | `operations.yaml` ships GST 5% (restaurant food) and GST 18% (packaged/beverage) both open-ended from the same date. That is correct and the new exclusion constraint permits it — it excludes overlap per *name*. But `tax_group` has no column saying which class a rate belongs to, so M04's `menu_item_variant.tax_group_id` is the only thing that will distinguish them, and M07 has no deterministic way to answer "the live rate" without one. Related to the successor-pointer row above; both are the same missing concept, which is that a tax group has an identity separate from its current row. **Decide both together at M06.** |
