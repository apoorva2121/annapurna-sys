# Backlog

Ideas that arrived mid-module. **Nothing here is scope** until it is promoted into
`docs/modules.md` deliberately, between modules — never during one.

This file exists because the vision document has 36 sections and the single most reliable way to
finish nothing is to act on all of them.

| One person who genuinely works for two restaurant groups cannot use one identifier | M01, 2026-09-10, **revised 2026-09-11** | Originally filed as "an ambiguous identifier locks that person out". An independent review found the sharper half: the clash check was org-scoped while login resolution is global, so *any tenant could deliberately take another tenant's identifier and lock its owner out permanently*. That is now fixed — creating a login refuses an identifier held anywhere in the product (`UserAccountRepository.identifier_is_taken`), and `tests/test_review_regressions.py` holds it. **The cost of that fix is this entry**: an accountant who really does work for two restaurant groups can no longer use one email for both, and now gets a plain "already in use" when the second group adds them. That is the right trade — an availability hole that any trial account could exploit beats an inconvenience for a rare, legitimate case — but it is a real regression in capability and should not be discovered later as a surprise. Proper fix is a per-tenant login surface (subdomain) or an organization picker, at which point identifiers can go back to being per-tenant unique. |
| Package `seed/` into the backend image | M01, 2026-09-11 | `make seed` reads `seed/organization.yaml`, which lives at the repository root while the backend's Docker build context is `./backend` — so the image cannot contain it. Compose mounts it read-only and the loader searches `SEED_DIR`, `/app/seed`, then the working copy, which covers local and a staging box running the same compose file. A standalone image (ADR 0005's deploy unit) would need the data inside it: either move the build context to the repo root, or have M15's generator ship the dataset as package data. **Do this with M15**, which owns the full seed generator anyway. |
| ~~Initialise shadcn/ui properly~~ **CLOSED 2026-09-11 (M02 chunk D)** | M01, 2026-09-11 | The entry said M00 never ran `shadcn init`. That stopped being true with `5271616`, which added `components.json` aliased to our paths and a genuinely shadcn-derived `Button` on `@radix-ui/react-slot`. M02 chunk D then vendored Select, Dialog, Sheet, Table, Switch and Label through the generator and adapted each to our tokens, so the library *is* the design system in practice and not only in `conventions.md`. | Global identifier uniqueness is enforced by code, not by the database | M01, 2026-09-11 | `user_account` constrains `(organization_id, email)` and `(organization_id, phone)` per tenant. The product now also requires identifiers to be unique *globally*, because login resolves across organizations — but that rule lives only in `_create_login` and the seed. Two concurrent creates in different organizations can both pass the check and both insert, and CLAUDE.md invariant 1 is explicit that this class of rule should be structural rather than conventional. **Deliberately not fixed in M01.** A global unique index would work, and would also permanently foreclose the per-tenant login surface (subdomain, or an organization picker) that the row below names as the proper fix — after which identifiers correctly go back to being per-tenant unique and the global index has to be dropped again. Adding a constraint we expect to remove is worse than carrying a documented race that requires an attacker to win a timing window against an account being created. Revisit **with** that row, not before: whichever is built first decides the other. |
| Lockout reveals whether an identifier exists | M01, 2026-09-11 | `AuthService._reject_if_locked` runs *before* the password is verified, so five wrong guesses against a real identifier return `429 auth.locked` while an identifier nobody holds returns `401 auth.invalid_credentials`. That is an enumeration oracle sitting next to a login path built specifically to avoid one. Found by an independent review of M01. **Accepted for now**, because the alternative is refusing to tell a locked-out waiter why they cannot sign in at 7pm on a Saturday. Fix properly with rate limiting by IP rather than by account, so the signal stops being per-identifier. Revisit in M14 with the rest of the security hardening. |
| Two stale tabs refreshing at once sign each other out | M01, 2026-09-11 | The single-flight in `shared/api.ts` is per-tab. Two tabs whose access tokens expire together each present the same refresh cookie; one is a replay, and `_handle_replay` correctly revokes the whole family — so a person with two tabs open over lunch is signed out of both. Correct behaviour from a stolen-token standpoint, poor behaviour from a real one. Fix needs cross-tab coordination (a `BroadcastChannel` lock, or moving refresh into a service worker). Not worth it in M01; worth it before staff actually use the product on a shared tablet. |
| Reset another employee's password from the UI | M01, 2026-09-11 | `POST /staff/employees/{id}/password` exists, is permission-gated and is tested; the M01 frontend deliverable list did not include a screen for it, so there is no button. An owner currently needs the API. Small — add it to the employee page when M02 touches that screen. |
| Share business-day test vectors between Python and TypeScript | M02, 2026-09-11 | The rule now has two implementations (`backend/app/core/business_day.py`, `frontend/src/shared/businessDay.ts`) and ADR 0004 forbids a third. They are held together by tests that use the same instants — but the instants are *transcribed* into each file, so a case added to one side is not added to the other, and the day they disagree is the day the UI shows a date the database does not hold. A shared fixture file both suites read would make the agreement structural rather than a matter of care. Not done now because it needs a home outside `backend/` and `frontend/`, which is a repository-layout decision worth making deliberately rather than mid-chunk. Do it when a third consumer appears, or when the two files first drift. |
| `date_trunc('day', created_at)` is forbidden by documentation only | M02, 2026-09-11 | ADR 0004 and the M02 spec both say reporting must never group on it, and `tests/test_business_day.py` proves the two genuinely disagree — but nothing *stops* a future report from writing it. There are no reports yet, so there is nothing to catch. When M13 lands, add a grep-style audit to `make check` over `app/` for `date_trunc` on a timestamp column, the way the seed and docs audits already work. Cheap then, meaningless now. |
| ruff's `DTZ` rules (naive datetime) are not enabled | M02, 2026-09-11 | CLAUDE.md invariant 4 is that time is stored UTC and aware; `business_date_of` refuses a naive datetime at runtime. `DTZ` would catch `datetime.now()` without a timezone at the lint stage instead, which is where it is cheap. Not enabled mid-chunk because it applies to the whole existing codebase and wants its own pass with its own review. Turn it on between modules and fix what it finds. |
