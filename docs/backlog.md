| Refresh-rotation grace window for honest double-refreshes | M02, 2026-09-11, **external review** | `refresh()` now claims the session row atomically, so two concurrent refreshes cannot both mint a session. | Expired idempotency keys are never swept | M07, 2026-09-13 | ADR 0010 says keys expire after 24 hours "swept by a nightly job". Expiry is **honoured** — an expired key can be claimed again — but no job deletes old rows, so `idempotency_key` grows by one row per money or stock write for ever. Harmless for months at pilot volume (one row per settle and per delivery, indexed on `expires_at`). **Un-defer with the first scheduled job** — the project has none yet — or when M15's 120-day generator makes the table's size measurable. |
| Input GST is apportioned pro rata by line value, which is an approximation on a mixed-rate invoice | M06, 2026-09-13 | `docs/compliance-rules.md` §A6 makes input GST part of the cost of stock for a 5%-scheme restaurant, and `ProcurementService._apportion` spreads the invoice's `tax_amount` across the lines by value. **Exact when every line carries one rate**, which for a single supplier's invoice is the ordinary case; wrong by the spread between rates when one invoice mixes, say, 5% vegetables and 18% packaged goods. The exact version needs a per-line `tax_amount` (a migration) or a per-item GST rate the product does not hold — `library/market-rates.yaml`'s `gst_rate` is research about a national market, not this supplier's bill. **Un-defer when a pilot restaurant's invoices routinely mix rates**, which is a question to ask at onboarding rather than to guess now. |
| Returns to supplier and credit notes are not modelled | M06, 2026-09-13 | A quality rejection **at the gate** is modelled (`quantity_rejected` + `rejection_reason`), because it happens on the weighing screen while the driver waits. A credit note issued three days later is a different thing: it is a legal document, so by G-13 checklist item 3 it wants its own table, its own numbering and its own immutability rule, and it needs a payables concept M06 deliberately has none of. Today the correction path is a `stock.adjust` movement with `ref_type='goods_receipt'`, which keeps the ledger honest and leaves the paperwork outside the product. **Un-defer when a pilot restaurant actually receives a credit note** and wants it reconciled. |
| Receiving reads each stock item twice per line | M06, 2026-09-13, **found by M06's own adversarial review** | `ProcurementService._post_lines` calls `_require_item` for the reprice, and `InventoryService.receive_stock` resolves the same item again for its own validation — two SELECTs per delivered line, so a 20-line delivery issues 40 where 20 would do. Not an N+1 on a list endpoint (the query-count assertions target reads), and a delivery is typed by a human a few times a day, so it is measured in microseconds nobody waits for.
