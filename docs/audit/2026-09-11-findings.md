## Security and correctness

### P1-1 · Failed-request bookkeeping is rolled back: lockout and replay revocation never persist
- **Where:** `backend/app/services/auth.py` — `login()` lines 104–106, `_record_failure()` 157–163,
  `refresh()` 257–259, `_handle_replay()` 277–291. `backend/app/core/db.py:38-41` (`get_session`).
  `backend/app/api/v1/auth.py:83-111` (routes commit only on success).
- **What happens:** every route follows *service flushes, route commits*. On a wrong password the
  service flushes `failed_attempts += 1` and raises; the route never reaches `session.commit()`;
  FastAPI 0.141 re-raises at the dependency's `yield`; `AsyncSession.__aexit__` → `close()` →
  **rollback**. Five wrong passwords never lock anyone. Same shape in `refresh()`: `revoke_family`
  runs, the caller raises `auth.session_invalid`, the revocation is rolled back — a thief who uses a
  stolen refresh token first keeps it; the legitimate user is the one logged out.
- **Why 262 tests miss it:** `backend/tests/conftest.py:85-88` overrides `get_session` with one
  shared `db_session` that is never closed between requests, so flushes persist inside the test
  transaction. No HTTP-level test asserts a 429 after five failures or a dead family after a replay.
- **Fix:** commit the failure counter and the replay revocation inside the service before raising
  (ADR 0010: services own transactions). Make the harness open a new session per request. Add the
  two HTTP-level regression tests. See remediation R1.
- **Status 2026-09-11, commit `b01a8b0` (found independently by running the manual script):**
  the **lockout half is fixed** — `_record_failure` now commits itself, and
  `tests/test_lockout_persistence.py` proves it across real commit boundaries using a new
  `fresh_database` fixture. **Still open:** `refresh()` → `_handle_replay()` is unchanged, so the
  family revocation is still rolled back with the 401; the `api` fixture in `conftest.py` still
  shares one session across requests (durability is opt-in per test, not the default); no
  HTTP-level replay test exists.

### P1-2 · Branch-local seniority guards a global account → cross-branch account takeover
- **Where:** `backend/app/services/employee.py` — `_rank_of()` 354–356 (resolves rank at
  `actor.restaurant_id` only), used by `reset_password()` 367–403, `deactivate_employee()` 217–250,
  `reactivate_employee()` 252–267. `backend/app/services/auth.py:184-202` (`_home_restaurant`
  picks the person's *first* branch).
- **Attack:** an org admin (rank 10 at head office) who also holds `manager` (rank 20) at branch B
  is visible to B's managers and resolves to rank 20 there. A B manager resets their password
  (`may_assign_rank(20, 20)` is true), signs in as them, and lands at head office with admin
  permissions. Every audit row afterwards names the victim. Same path lets a branch manager
  deactivate the org owner if the owner holds any role at that branch.
- **Fix:** account-level actions (password, deactivate, reactivate, update) are judged against the
  target's most senior role **anywhere in the organization**. See remediation R2.

### P1-3 · The deployed app cannot sign in: same-origin is assumed, not implemented
- **Where:** `frontend/src/shared/api.ts:7` (`API_BASE = '/api/v1'`, relative) and 130–155 (`send`
  sets no `credentials`); `frontend/Dockerfile:34-48` (runtime nginx has no `location /api/`);
  `backend/app/api/v1/auth.py:55-67` (`SameSite=Lax` cookie); ADR 0005 (SPA on Cloudflare Pages,
  API on Cloud Run — two origins).
- **What happens:** with the runtime image, `fetch('/api/v1/...')` returns `index.html` with a 200.
  With two origins, the relative base is wrong; an absolute base without `credentials: 'include'`
  never sends the refresh cookie; with it, `SameSite=Lax` drops the cookie on a cross-site POST;
  with `SameSite=None` the refresh endpoint is CSRF-reachable and there is no CSRF token.
  `scripts/smoke.py` tests the Vite dev server, never the runtime images.
- **Fix:** one origin, decided now. Recommended: FastAPI serves the built SPA (one Cloud Run
  service). Add `make smoke-prod` against the runtime images. Refuse `CORS_ORIGINS=*` outside
  local. See remediation R4.

### P1-4 · Passwords and phone numbers reach Sentry on the first unhandled exception
- **Where:** `backend/app/main.py:80-89` (`configure_sentry`); `backend/app/core/logging.py:25-36`
  (`SENSITIVE_KEYS`, exact-key match) and 107–117 (`RedactingFilter` installed only on the stdout
  handler).
- **Verified against the installed `sentry-sdk 2.69.1`:** `max_request_body_size` defaults to
  `"medium"` (bodies ≤ 10 KB are attached regardless of `send_default_pii=False`); the default
  `EventScrubber` denylist matches keys exactly — `password` is scrubbed, `new_password`,
  `current_password`, `initial_password`, `identifier`, `login_identifier`, `phone`, `full_name`
  are not. Sentry's `LoggingIntegration` attaches its own handlers to the root logger, so
  `logger.exception(..., extra=...)` reaches Sentry **unredacted** — the "cannot be bypassed" filter
  is bypassed by the integration configured next to it.
- **Fix:** `max_request_body_size="never"`, an extended recursive `EventScrubber`, `before_send` /
  `before_breadcrumb` that reuse `redact_value`; substring-match `SENSITIVE_KEYS`. See R3.
  **Do not set `SENTRY_DSN` anywhere until R3 is done.**

### P1-5 · The account lockout is an owner-lockout button for anyone on the internet
- **Where:** `backend/app/services/auth.py:135-163`; `backend/app/core/config.py:63-64`;
  `docs/security.md` A07 promises "rate limiting on login" — nothing implements it;
  `backend/Dockerfile:58` runs uvicorn without `--proxy-headers`, so `_client_ip`
  (`auth.py:51-52`) sees the load balancer.
- **What happens (once P1-1 is fixed):** five wrong guesses against `owner@…` lock the owner for 15
  minutes, from any IP, repeatable forever, during service.
- **Fix:** progressive per-identifier delay instead of a hard lock; per-IP budget in a
  `login_attempt` table; proxy headers; log every denial. See R5.

### P1-6 · Lateral takeover and unguarded edits inside a branch (Medium)
- **Where:** `backend/app/core/permissions.py:128-137` (`may_assign_rank` allows equal rank);
  `backend/app/services/employee.py:198-213` (`update_employee` has no seniority check at all).
- **What happens:** a manager resets a peer manager's password and acts as them (audit attributes
  it to the victim); a manager rewrites the owner's name, phone and date of birth.
- **Fix:** password reset requires strictly more senior (owner-on-owner excepted); add the guard to
  `update_employee`; add `user_account.password_reset_required` so a reset is never a silent login.
  See R2.

### P1-7 · Cross-tenant identifier existence oracle, still racy (Medium)
- **Where:** `backend/app/repositories/account.py:26-48`; `backend/app/services/employee.py:164-181`;
  `backend/app/schemas/identity.py:135` (`login_identifier` has no validation or normalisation).
- **What happens:** `identifier_is_taken` is global, so any trial tenant can learn whether an email
  or phone is registered anywhere in the product (409 vs 201). The check is check-then-insert with
  only per-org unique constraints, so two tenants can still create the same identifier concurrently.
  `"+91 98765 43210"` and `"9876543210"` are two different logins today.
- **Fix:** normalise identifiers at the boundary (lowercase email, E.164 phone) — not contested.
  For the race, `docs/backlog.md` (entry added in `b01a8b0`) deliberately declines a global unique
  index because the proper fix is a per-tenant login surface, after which the index would have to
  come off again. That is a defensible call; the race needs an attacker to win a timing window.
  R6 therefore treats "index now vs per-tenant login surface" as a **DECIDE**, and the existence
  oracle (409 vs 201 across tenants) stays open until the per-tenant surface lands.

### P1-8 · Refresh rotation without a grace window logs staff out on restaurant WiFi (Medium)
- **Where:** `backend/app/services/auth.py:248-291`; `frontend/src/shared/api.ts:166-199`;
  `docs/backlog.md` "two stale tabs".
- **What happens:** a retried request after a timeout, or two tabs on a shared tablet, present the
  same token twice → the family is revoked → everyone is signed out. Daily on the network ADR 0010
  describes.
- **Fix:** idempotent rotation for ~60 s (`replaced_by_session_id`; a token presented inside the
  window returns the same successor); `BroadcastChannel` lock client-side. See R6.

### P1-9 · Argon2 runs on the event loop (Medium now, High at M08)
- **Where:** `backend/app/core/security.py:56-84`, called synchronously from
  `AuthService.login/refresh/change_own_password` and `EmployeeService.create_employee/reset_password`.
- **What happens:** each verification blocks the uvicorn worker for 150–300 ms (t=3, 64 MiB, p=4).
  A shift-start login burst stalls the KDS stream and every waiter tap.
- **Fix:** `asyncio.to_thread` wrappers; cache the `PasswordHasher`. See R1.

### P1-10 · `organization.plan` is never enforced (Medium; also the billing hook)
- **Where:** `backend/app/models/tenancy.py:40`; `backend/app/services/auth.py:184-202`;
  `backend/app/api/deps.py:48-93`.
- **Fix:** refuse login/refresh/`current_actor` for `suspended`/`cancelled`; add `trial_ends_at`;
  add `require_entitlement()` next to `require_permission()`. See R5.
